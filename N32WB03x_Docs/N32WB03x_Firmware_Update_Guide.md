**Version:** V1.3
**Date:** 2024.04.04
**Manufacturer:** NSING Technologies Pte. Ltd. (nsing.com.sg)

## Introduction

This document presents the principle of N32WB03x firmware update and examples to help users familiarize themselves with the firmware update process for rapid development.

**Functional features of N32WB03x firmware update:**

- Support firmware update through serial port.
- Support firmware update through BLE.
- Support BLE MTU 20–244 bytes.
- ECC digital signature is used to verify the firmware validity for BLE update.
- BLE "dual bank" update for faster updates and version rollback support.
- BLE "single bank" update for when user programs need more space.
- The system automatically selects "dual bank" or "single bank" update (no user input required).
- Update speed can be controlled through mobile APP for compatibility with all phone manufacturers.

## 1. Demonstration by Examples

### 1.1 Demonstration of JLINK Programming

**Directory:** `N32WB03x_SDK\utilities\dfu\Image\JLINKProgrammingDemo`

Double-click `JLINKProgramming.bat` to execute the following steps:

1. **Step 1:** BootSetting Bin is generated by NSUtil tool. "Bootsetting created successfully!" confirms generation.
2. **Step 2:** JLink erases the chip's Flash.
3. **Step 3:** Program `MasterBoot.bin` to the chip's Flash.
4. **Step 4:** Program `Bootsetting.bin` to the chip's Flash.
5. **Step 5:** Program `APP1.bin` to the chip's Flash.
6. **Step 6:** Program `APP2.bin` to the chip's Flash.
7. **Step 7:** Program `ImageUpdate.bin` to the chip's Flash.
8. **Step 8:** Reset the chip.

JLINK successively executes erase, write MasterBoot.bin, Bootsetting.bin, APP1.bin, APP2.bin, ImageUpdate.bin, and reset. If programming fails, the chip may be in DEEP SLEEP — try executing `JLINKProgramming.bat` before powering up the chip.

**Binary file sources:**

| File | Source |
|---|---|
| `MasterBoot.bin` | MasterBoot Keil Project (Keil → Option for Target → User → Run #2) |
| `Bootsetting.bin` | NSUtil python tool |
| `APP1.bin` / `APP2.bin` | AppOTA Keil Project (Keil → Option for Target → User → Run #2) |
| `ImageUpdate.bin` | ImageUpdater Keil Project (Keil → Option for Target → User → Run #2) |

**Testing activation:**

- Modify `bank1_activation=no`, `bank2_activation=yes` to start the Bank 2 program.
- View serial port output via chip PB1 (115200 N 8 1), or observe LED blinking frequency (APP1: 100ms, APP2: 500ms).
- Search for Bluetooth device with "NATION" broadcast name.
- Modify `bank1_activation=no`, `image_update_activation=yes` to run ImageUpdate.

> **Note:** Only one program can enable activation at a time.

**Directory:** `N32WB03x_SDK\utilities\dfu\Image\UartProgrammingDemo`

7. Double-click `UartFirmwareUpdate.bat` to view results.

JLINK programs the bin file into Bank 1 by default (PB0 pin pulled up). Serial port update loads the new program into Bank 2 by default (PA6 pin pulled up). To update to Bank 1 instead, modify `app_bin=.\Image\APP1.bin`, `app_start_address=0x01004000`.

## 2. Distribution of FLASH Memory

FLASH address range: `0x0100_0000` – `0x0103_FFFF` (256KB total)

| Name | Address Range | Size | Description |
|---|---|---|---|
| **Master Boot** (program) | `0x0100_0000` – `0x0100_1FFF` | 8 KB | Program entry after power on. Reads partition table, jumps to program. Serial port update function. |
| **Bootsetting** (data / Partition Table) | `0x0100_2000` – `0x0100_2FFF` | 4 KB | FLASH partition table |
| **APP Data** (Bond Table + User Data) | `0x0100_3000` – `0x0100_3FFF` | 4 KB | Storage binding list (~500 bytes for 5 devices). Remaining space for user-defined data. |
| **APP 1** (Bank 1) | `0x0100_4000` – `0x0101_FFFF` | 112 KB | User program 1 storage area |
| **Free Space / APP 2** (Bank 2) | `0x0102_0000` – `0x0103_BFFF` | 112 KB | Reserved space or user program 2 storage area |
| **Image Update** (program) | `0x0103_C000` – `0x0103_FFFF` | 16 KB | Reserved space or "single bank" update program |

```
┌─────────────────────────────────┐ 0x0103_FFFF
│  Image Update (16 KB)           │
├─────────────────────────────────┤ 0x0103_C000
│  APP 2 / Free Space (112 KB)    │
│  (Bank 2)                       │
├─────────────────────────────────┤ 0x0102_0000
│  APP 1 (112 KB)                 │
│  (Bank 1)                       │
├─────────────────────────────────┤ 0x0100_4000
│  APP Data (4 KB)                │
├─────────────────────────────────┤ 0x0100_3000
│  Bootsetting (4 KB)             │
├─────────────────────────────────┤ 0x0100_2000
│  Master Boot (8 KB)             │
└─────────────────────────────────┘ 0x0100_0000
```

**Key notes:**

- MasterBoot provides program jump entry and serial port update.
- Bootsetting provides program jump and update shared data.
- If more APP Data space is needed, use external storage or modify FLASH distribution (contact technical support).
- APP1 = user program on Bank 1, APP2 = user program compiled on Bank 2.
- ImageUpdate = program for "single bank" update.

## 3. Data Structure

### 3.1 Bootsetting

| Size (Bytes) | Name | Description |
|---|---|---|
| 4 | Bootsetting CRC | Bootsetting data check value |
| 4 | MasterBoot Force Update | Forced serial port update for MasterBoot. `1`: serial port update. Default: `0xFFFFFFFF` |
| 4×10 | Bank 1 partition | 4B: start address, 4B: program size, 4B: CRC, 4B: version, 4B: activation code (1=active), 4×5B: reserved |
| 4×10 | Bank 2 partition | Same structure as Bank 1 |
| 4×10 | Image Update partition | Same structure as Bank 1 |
| 64 | Public key | Used for ECC signature verification |

**CRC calculation:**

```
Bootsetting CRC = CRC32(MasterBoot Force Update + Bank 1 partition + Bank 2 partition + Image Update partition + Public key)
```

---

### 3.2 Init Packet (Serial Port Update)

| Size (Bytes) | Name | Description |
|---|---|---|
| 4 | CRC | Data check value |
| 4 | App_start_address | First address of new firmware |
| 4 | App_size | Size of new firmware (bytes) |
| 4 | App_crc | Check value of new firmware |
| 4 | App_version | Version of new firmware |
| 4×10 | Reserve | Reserved |

---

### 3.3 DFU Setting

Auto-generated by `NSUTIL.exe` for Bluetooth update. Used for signature verification and integrity check.

| Size (Bytes) | Name | Description |
|---|---|---|
| 4 | CRC | DFU_SETTING data check value |
| 4×4 | APP 1 parameter | 4B: start address, 4B: size, 4B: CRC, 4B: version |
| 4×4 | APP 2 parameter | Same structure |
| 4×4 | Image Update parameter | Same structure |
| 64 | Signature | HASH data + signature file based on private key |

**Calculations:**

```
CRC = CRC32(APP 1 parameter + APP 2 parameter + Image Update parameter + Signature)
Signature = ECC_ECDSA_SHA256_NIST256P(APP 1 parameter + APP 2 parameter + Image Update parameter)
```

## 4. Update Process

### 4.1 Serial Port Update Process

1. User application sets the `MasterBootForceUpdate` variable in bootsetting data.
2. Software resets, enabling the MasterBoot program.
3. MasterBoot Force Update variable activates the serial port update process.
4. MasterBoot receives new firmware through serial port.
5. Erases original firmware in Bank 1 area.
6. Writes new firmware.
7. Activates new firmware.
8. Jumps to new firmware for execution.

---

### 4.2 Update Process of Bluetooth Dual Bank

"Dual bank" update works by updating APP1 with APP2, or vice versa.

**Advantages:** Faster update speed, higher stability.
**Disadvantages:** User program can only use half of the FLASH area. An additional Bank 2 bin file is needed for the update package.

---

### 4.3 Update Process of Bluetooth Single Bank

"Single bank" update works by updating the APP1 program with the ImageUpdate program.

**Advantages:** User program can use all FLASH regions.
**Disadvantages:** Slow update speed, Bluetooth disconnect/reconnect causes possible instability, no backup if update fails.

## 7. Examples Explanation

**Directory:** `N32WB03x_SDK\projects\n32wb03x_EVAL\dfu\`

### 7.1 MasterBoot Explanation

- `Masterboot()`: Reads the bootsetting partition table and directly jumps to the activated firmware with complete verification.
- Illuminates two LEDs for indication.
- Initializes simple scheduling.
- Initializes the serial port.
- Waits for serial port interrupt receiving data.
- Analyzes and handles serial port commands, responds to the upper computer.

---

### 7.2 AppUsart Explanation

- Serial port update APP 1 program.
- Judges whether currently in Bank 1 or Bank 2. LED1/LED2 illuminate for Bank 1/Bank 2 respectively.
- Initializes the serial port.
- Waits for serial port interrupt receiving data.
- Handles serial port command, responds to PC, writes forced serial port update flag, and service jumps to MasterBoot program.

---

### 7.3 AppOTA Explanation

- Configures MAC address of Bluetooth.
- Configures the name of Bluetooth broadcast.
- Adds IUS (Image Update Service).
- Handles CC commands.
- Handles RC commands and data.

**Creating an update package — Keil configuration:**

- Modify `IROM1` in Keil's Options for Target and the `Run #2` parameter:
  - **Bank 1 (APP1):** `IROM1: 0x1004000`, `Run #2: APP1` → generates `APP1.bin` under Image folder.
  - **Bank 2 (APP2):** `IROM1: 0x1020000`, `Run #2: APP2` → generates `APP2.bin` under Image folder.

---

### 7.4 ImageUpdate Explanation

- Adds one to the last bit of the Bluetooth MAC address (to differentiate from the main app's BLE device).

---

## 8. Explanation of Encryption

- Enable the macro `OTA_ECC_ECDSA_SHA256_ENABLE` in AppOTA and ImageUpdate programs to enable update signature verification.
- The project includes ECC verification interface files.
- When receiving `dfu_setting` data, the embedded side performs signature verification.
- The update package generation tool uses ECC to sign and encrypt firmware parameters (CRC, size, etc.) and saves them in `dfu_setting`.
- After receiving `dfu_setting`, the embedded side uses the known **public key** to verify the signature.
- Update (FLASH erase/write) only starts when signature verification succeeds.
- Only unique firmware information is encrypted and signed, accelerating verification while protecting the firmware update.
